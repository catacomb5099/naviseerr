# Log in with Authentik, and nothing else (19-10-2026)

**Changed 19-10-2026 22:40, the owner's call: "Change it: require login as soon as Save and test
succeeds."** The first build of the evening turned the login on at the first successful sign-in; from
this change a successful `PUT /settings/login` writes the row with `enabled = true`, so there is no
"saved but not on yet" state: the very next request without a session gets the login screen, and
signing in returns to the page you were on (the `to` return address). The callback no longer touches
`enabled`. What guards against locking yourself out is Save and test's own check (a wrong Client ID,
secret or Redirect URL is refused and nothing is saved); the way back if Authentik itself goes away stays
the one-line `UPDATE login_settings SET enabled = false`. The flip back is one line (`enabled = TRUE`
out of `SAVE_SQL`, `setEnabled(true)` back into the callback). The text below is updated in place.

## The problem

Anyone who could reach the web app could search, start downloads and press "Make this week's
playlists now" (a 90-minute run). There was no identity anywhere: no session, no filter; the README
said "the web app has no login" and asked people not to forward its port. The owner runs Authentik
already and wants the web app reachable from the internet behind their own proxy.

## The decision

- **Authentik is the only login.** No accounts of its own, no passwords, no setup code, nothing that
  sends anyone to read a log. The owner's words: "forget the app's own login, just use Authentik, and
  have a continue with Authentik button". Who may log in is decided in Authentik (bind the application
  to your own user there); naviseerr shows no name and has no roles. Nothing in it is per-user.
- **Two modes, one row.** `login_settings` (V16) holds the Authentik address, Client ID, Client secret
  and `enabled`. No row, or `enabled = false` = OPEN: every route as it always was, for local use.
  `enabled = true` = every route needs a session, except the four routes that exist to get one and a CORS
  preflight (`AuthFilter`, default-deny). `enabled` is set by a **successful "Save and test"** (since
  22:40; before that by the first successful sign-in): the row is written with `enabled = true` in one
  statement, and the filter reads it on every request, so the request after the PUT is already behind
  the door. A wrong Client ID, secret or redirect URL cannot lock the owner out because Save and test
  tries all three at Authentik's token endpoint first and refuses with nothing saved; and since a pass is the
  switch, only Authentik's own token error about the bogus code counts as one (a 5xx, an HTML page from a
  proxy in front, or a token issued for a code that does not exist fail the test too, so the door never
  shuts on a provider that could not complete the sign-in; review fix). "Turn off Authentik
  login" in Settings (needs a session) puts `enabled` back to false and drops every session; the settings
  stay, and the next Save and test (secret field left empty) turns it back on.
- **Connected from Settings, not from a file.** `GET|PUT|DELETE /settings/login` (the fields Immich's
  OAuth settings have). PUT fetches `{issuer}.well-known/openid-configuration` first and names the
  problem in one plain sentence (unreachable, 404 = wrong slug, not an OpenID document, no scheme),
  which is the Audiobookshelf "Auto-populate" check and better than Immich, which only logs it. The
  redirect URL to paste into Authentik is shown there, computed from the request: `X-Forwarded-Proto`
  + `Host` + `X-Forwarded-Prefix` + `/auth/authentik/callback`. The web app's Caddy sets the prefix
  header (`/api`, one line), so an install shows `https://your.address/api/auth/authentik/callback`
  and a developer's bare jar `http://localhost:8080/auth/authentik/callback`.
- **OpenID Connect authorization code with PKCE and the client secret, hand-rolled** on the `WebClient`
  the project already uses. `GET /auth/authentik/start` makes state, nonce and a PKCE verifier (32
  random bytes each), keeps them with the redirect URL and the return address in ONE HttpOnly
  SameSite=Lax cookie `naviseerr_login` (ten minutes, JSON as base64url) and redirects to the
  authorization endpoint with `scope=openid` (we need `sub` and nothing else). `GET /auth/authentik/callback`
  checks the state against that cookie, POSTs code + verifier + client id + client secret to the token
  endpoint (`client_secret_post`), reads `iss`, `aud`, `exp`, `nonce`, `sub` from the ID token's payload,
  opens OUR session and sets OUR cookie, clears the login cookie, and lands on the return address
  (it does not touch `enabled`). Any failure is a 400 page with one sentence and a link back, never a session; `start`
  answers the same page (404 nothing connected, 502 Authentik unreadable), since a browser follows it.
- **No ID-token signature check, on purpose.** OpenID Connect Core 3.1.3.7 step 6: when the ID token is
  received directly from the token endpoint over TLS, TLS server validation may stand in for the
  signature check. That also sidesteps a real trap: an Authentik OAuth2 provider signs with RS256 and a
  self-signed certificate by default, a Proxy provider with HS256; a JWKS-based decoder handles only the
  first. A LAN install reaching Authentik over plain http trusts its own network for this, and the
  README says so. Flip, six lines: call `userinfo_endpoint` with the access token and take `sub` there.
- **A session is a row** (`sessions`, V17: `session_id`, `subject`, `created_at`, `expires_at`) and the
  cookie `naviseerr_session` (HttpOnly, SameSite=Lax, Path=/, 30 days, Secure when the request came
  over HTTPS: `X-Forwarded-Proto`, read by hand because `@EnableWebFlux` keeps Boot's forwarded-header
  support off). A restart keeps everyone signed in; logout deletes the row; expired rows are swept at
  each sign-in. `Lax` + JSON bodies = no CSRF filter: a cross-site form POST cannot send
  `application/json`, and Lax withholds the cookie on cross-site POSTs.
- **Log out = our session only.** Authentik's own session stays, as Grafana and Immich do, so the next
  "Continue with Authentik" is one click. Without a cookie nothing is cleared and nothing sent back, so a
  cross-site form POST (Lax withholds the cookie) cannot log the owner out. Flip (documented, not built): redirect to the discovery
  document's `end_session_endpoint`.
- **The return address.** `start?to=<url>` is believed when it is a plain path, on the request's own
  host, or on a listed `auth.allowed-origins` origin (the developer's Vite); anything else lands on `/`,
  including whatever `java.net.URI` rejects (a backslash, which browsers read as a slash).
  Needed because the developer setup lands the callback on the server's port, where `/` is the API.
- **Not Spring Security's OAuth2 client.** It would need two starters (not in the local cache for
  Boot 4.0.2 / Security 7.0.2) and five custom beans to stop it owning the session (a DB-backed
  `ReactiveClientRegistrationRepository` with a blocking discovery call, cookie-based authorization
  request repository, security-context repository, success handler, entry point) plus a per-request
  on/off matcher: as much glue as the whole hand-rolled flow (about 500 main lines over nine small
  classes, no new dependency), with CSRF and default headers to switch off on top.
- **CORS: only the web app's own address, and a list.** A `CorsWebFilter` ahead of the door (so the
  cross-origin dev browser can read a 401) with credentials for `auth.allowed-origins` only (default the
  dev client `http://localhost:5173`; the Docker image sets the list empty, so an install allows no
  other address, as Navidrome and Jellyfin ship CORS off). A request whose `Origin` names the request's
  own `Host`, whatever the scheme, is the web app calling its own server and skips the filter: that is
  what keeps the install working behind an HTTPS proxy, where the server sees plain HTTP and Spring's
  own same-origin test would call it cross-origin. `.env.example` keeps the line commented out because
  an empty `AUTH_ALLOWED_ORIGINS=` is "none", not the default. The same list says where a sign-in may land.

## Why this shape

- The reference set: Immich ("Login with OAuth" button; Issuer URL, Client ID, Client Secret in its
  settings, discovery suffix optional), Grafana ("Sign in with <name>", PKCE on, `signout_redirect_url`
  as the opt-in provider logout), Audiobookshelf (issuer "Auto-populate" check, "test it before turning
  off local authentication"). Jellyfin's SSO plugin is the "how not to": JSON config, a button pasted as
  HTML. Spotify / YouTube Music set the "stay signed in" length.
- The first build (same day, morning: own accounts with bcrypt, a first-run screen, a setup code from
  the server log, two throttles) was closed by the owner in the evening: "having to check the logs, that's
  not user-friendly ... We're not doing that." What survives from it, almost verbatim: the default-deny
  filter, the sessions table minus `user_id`, the cookie rules, the Docker health check on
  `/auth/session`, and the own-origin CORS idea (next PR).

## Flippable

- Session length: `auth.session-days` (application.yaml), 30.
- Which addresses the sign-in may land on: `auth.allowed-origins` (`AUTH_ALLOWED_ORIGINS`).
- Provider logout on "Log out": redirect to `end_session_endpoint` (kept in `OpenIdConfiguration`, unused).
- Signature check instead of trusting TLS: `userinfo_endpoint` with the access token.
- Remember the first subject and refuse every other one (an app-side owner lock): one column and one
  `if` in the callback; not built, the owner binds the application to their user in Authentik instead.
- Enforce at the first sign-in instead of at "Save and test" (the first build's rule, 19-10-2026
  until 22:40): take `enabled = TRUE` out of `LoginSettingsRepository.SAVE_SQL` and put
  `.then(settings.setEnabled(true))` back into `AuthController.startSession`. One line each way.
- Cookie: `SameSite=Lax` -> `Strict` would log you out when arriving by link or from Authentik's redirect.

## Known ceilings (stated, not fixed)

- **First-run window.** Until Save and test has succeeded, anyone who can reach the app can connect
  THEIR Authentik, which then locks the owner out. Accepted by the owner for local-first installs; the
  README says "connect Authentik before you open the proxy to the internet". Recovery:
  `UPDATE login_settings SET enabled = false` (README, Troubleshooting), no restart needed.
- **Connected, then locked out before the first sign-in.** Save and test shuts the door at once; if
  the sign-in that follows fails for a reason the check could not see (Authentik's user binding keeps
  you out, say), you are outside with the settings saved. The same UPDATE is the way back; the check
  catches the common causes (wrong Client ID, secret or Redirect URL, a token endpoint that cannot answer)
  before anything is saved.
- **Authentik gone = locked out** until it is back, by design; the same psql line is the way in.
  An env override (`LOGIN_OVERRIDE=open`) is a four-line flip if the owner wants a no-terminal recovery.
- **Save and test reaches out.** In open mode anyone on the network can point Save and test at any address
  the server can reach (`<address>.well-known/openid-configuration`, then the token endpoint it names) and
  learn status-level facts (reached, 404, not OpenID); nothing is echoed. One more reason not to expose an
  install before Authentik is connected.
- The client secret is stored as typed in Postgres (like the slskd API key and curator token in
  `/config`); `GET` never returns it and nothing logs token answers.
- Cookies ignore ports: on one machine, several naviseerr instances on `localhost` share the cookie
  name; a session id from another instance is simply unknown here (401, log in again). Harmless.
- **The Chrome extension (separate repo) is another origin.** With the allowlist it gets a bodiless 403 on
  every call, login on or off, until `chrome-extension://<its id>` is in `auth.allowed-origins` (the base
  answered `*` to everyone, so this is a change for the extension against a dev server too); host
  permissions in the extension do not help, the server refuses before any handler. It also needs
  `credentials: 'include'` and a 401 wording before it works with the login on. Flip for "no setup": a
  second `CorsConfiguration` for unlisted origins with `allowedOriginPatterns("*")` and no credentials
  (a few lines in `WebConfig.corsWebFilter`), so they read answers without the cookie as before.
