# A login: your own account, or your own login proxy (19-10-2026)

## The problem

Anyone who could reach the web app could search, start downloads and press "Make this week's
playlists now" (a 90-minute run). There was no identity anywhere: no users table, no session, no
filter; the README said "the web app has no login" and asked people not to forward its port. The
owner asked for "auth using authentik or basic username and password".

## The decision

- **Own login, on by default.** The first open of the web app shows "Create your account" (as
  Jellyfin's setup wizard and Navidrome's first screen do); after that a username and password screen.
  Exactly one account for now. `users.role` exists so more accounts later need no migration.
- **A session is a row.** `POST /auth/login` stores a random 32-byte id in `sessions` and sets it as
  the cookie `naviseerr_session` (HttpOnly, SameSite=Lax, Path=/, Max-Age 30 days, Secure when the
  request came over HTTPS: the proxy's `X-Forwarded-Proto`, which the web app's Caddy passes on from a
  proxy on a private address). A restart keeps everyone signed in; logout deletes the row; expired rows are
  swept at each login. No JWT, no signing key to persist, no Spring Session.
- **Default-deny filter.** `AuthFilter` answers `401 {"message":"Log in to Naviseerr"}` to everything
  without a live session, except `GET /auth/session`, `POST /auth/login`, `POST /auth/setup`,
  `POST /auth/logout` (a dead cookie still gets cleared) and `OPTIONS` (CORS preflight). A new endpoint is protected without anyone remembering; `/status`
  (Soulseek name, library path) is behind the login too.
- **bcrypt from `spring-security-crypto`, not the Security starter.** The starter would still need the
  same session store and login controller (Spring Session has no R2DBC store; the WebFlux form login
  redirects, which a single-page app does not want) and adds a CSRF filter to disable, a generated
  password in the log and default headers on every API answer. The filter is ~60 lines.
- **Your own login proxy = `AUTH_REQUIRED=false` + one Caddy snippet** in the web-app container
  (`import /etc/caddy/conf.d/*.caddy` in the client's Caddyfile; `deploy/authentik.caddy` here). Sonarr
  calls this "External": the proxy authenticates, naviseerr trusts whoever gets through and shows no
  name. Not Sonarr's "disabled for local addresses": behind the web app's proxy every request is local,
  and that option is how Sonarr got CVE-2026-30975.
- **Login throttle**: five failed attempts for one username within 20 seconds answer 429 for the rest
  of the window (Navidrome's `AuthRequestLimit` / `AuthWindowLength`). In memory, per process.
- **Wording never says which half was wrong**, and an unknown name costs the same bcrypt check as a
  wrong password, so neither the text nor the time lists the accounts.
- **Client first.** The web app treats a 404 on `GET /auth/session` as "no login on this server" and
  works unchanged against an older server; the old web app against the new server would read 401
  everywhere. So the client PR merges before the server PR, and `docker compose up -d --build` after
  both is consistent.

## Why this shape

- The reference set is admin-type self-hosted apps (Navidrome, Jellyfin, Sonarr, Audiobookshelf, slskd):
  all have their own users, the first created in-app, a JSON login plus a cookie or token, and SSO as
  "the proxy did it" or OIDC later. Spotify, YouTube Music and Apple Music set the "stay signed in"
  length and the avatar-menu "Log out".
- `SameSite=Lax` plus JSON bodies is why there is no CSRF filter: a cross-site form POST cannot send
  `application/json`, and Lax withholds the cookie on cross-site POSTs.
- CORS became a `CorsWebFilter` ahead of the auth filter, with origin patterns and credentials, because
  the handler-level mapping could not put CORS headers on a 401 written before routing and
  `allowedOrigins("*")` cannot be combined with credentials. The Docker install is same-origin anyway.
- The Docker health check moved to `/auth/session` (always 200); `/downloads/active` is 401 now.

## Flippable

- Session length: `auth.session-days` (application.yaml), 30.
- Off switch: `AUTH_REQUIRED=false`; in the Docker install as `AUTH_REQUIRED: "false"` under the
  naviseerr service's `environment:` (compose.yaml does not pass it on from `.env`).
- Throttle: `LoginThrottle.MAX_FAILURES` (5) and `WINDOW` (20 s).
- Cookie: `SameSite=Lax` → `Strict` would log you out when arriving by link; `Secure` follows HTTPS and
  cannot be forced on a plain-HTTP LAN install (the browser would drop it).

## Known ceilings (stated, not fixed)

- One account, no password change, no roles: the reset path is the README's "Forgot your password"
  recipe (delete the rows; the first-run screen comes back).
- naviseerr never learns the Authentik username (nothing is per-user today). Navidrome-style header
  trust (`AUTH_PROXY_HEADER`) is the natural next PR when something is.
- The Chrome extension (separate repo) needs `credentials: 'include'` on its three fetches and a 401
  wording; until then it reads a 401 as "not answering".
- The throttle resets on restart and is per process.
- Two first-run screens submitted in the same instant can both make an account (READ COMMITTED);
  normally the second sees the first's row and gets 409. Passwords are capped at 72 bytes, bcrypt's limit.

## Addendum, 19-10-2026 (evening): an install the internet can reach

The owner's new context: the web app will sit behind a reverse proxy on their own domain. Goals in
their words: stop bots and novice attackers (hammering search until YouTube Music blocks the
server, starting downloads until the disk fills); nobody but the owner may ever create an account;
one account, no roles; no bypasses. Four small changes on top of the login:

- **A setup code for the first account** (`SetupCode`). While no account exists, the server makes one
  random `xxxx-xxxx-xxxx` (SecureRandom, 31 unambiguous characters, so 31^12 codes) at start, prints
  it in a banner at INFO and, when the install's data folder is known (`install.data-dir`, i.e.
  `NAVISEERR_DATA_DIR`; or `auth.setup-code-file`), writes it owner-only to `config/setup-code.txt`.
  `POST /auth/setup` needs it: wrong is `401 Wrong setup code`, counted by the login throttle under the
  name `setup`; right makes the only account, voids the code and deletes the file; once an account
  exists any code is `409`; a web app that sends none is `400 This web app is older than the server:
  update it`, so an old web app never opens anything. Never printed again once the account exists; a
  restart before use prints a new one (so the "forgot your password" recipe ends with a restart).
  Followed: Jupyter (a token in the log), Grafana (admin password in the log on first run), Vaultwarden
  (`SIGNUPS_ALLOWED=false` + admin token), Navidrome's one-time "Create Admin". Rejected: an env-set
  password (lands in compose files and shell history), "allow setup only from private addresses"
  (behind the web app's proxy every request is local: the Sonarr CVE-2026-30975 shape again).
- **A cap for everyone** (`LoginThrottle`): thirty failed login or setup attempts in a minute, under any
  names, answer `429 Too many attempts, wait a minute` to all for the rest of that minute. The per-name
  rule (Navidrome's 5 in 20 s) never trips for a bot cycling through names; this one does, and it also
  bounds bcrypt time and log volume. The owner waits out the same minute during an attack: stated, and
  Authentik in front is the way to never pay it. In memory, per process (ponytail comment).
- **Every failure is one WARN line with the caller's address**: `Login failed for "<name>" from
  <address> (<n> of 30 failures this minute for everyone)`, plus one line when the cap is reached. The
  address is the FIRST hop of `X-Forwarded-For` only when the direct peer is on a private, loopback or
  link-local address (the install's Caddy, which itself trusts `X-Forwarded-For` only from
  `private_ranges`); otherwise the peer itself. A caller on the internet is never believed about who it
  is; a forged header from a LAN peer would only forge the log line, since nothing is throttled per
  address. Control characters in a name print as `?` so a name cannot forge a line. Fail2ban-ready.
- **CORS allowlist** (`WebConfig`): `allowedOriginPatterns("*")` with credentials echoed any origin
  back (flagged in the safety review of #174). Now `auth.allowed-origins` (default
  `http://localhost:5173`, the dev client) with credentials; a request whose `Origin` names the
  request's own `Host`, whatever the scheme, is the web app calling its own server and skips the
  filter, which is what keeps the compose install working behind an HTTPS proxy (the server sees HTTP,
  Spring's own same-origin test would call that cross-origin). Any other origin gets no
  `Access-Control-Allow-Origin` and a 403; requests with no `Origin` are untouched.
- **Browser hardening headers** in the web app's Caddyfile (naviseerr-client): `X-Content-Type-Options
  nosniff`, `X-Frame-Options DENY`, `Referrer-Policy strict-origin-when-cross-origin`,
  `Permissions-Policy camera=(), microphone=(), geolocation=()`, and `Cache-Control no-store` on `/api`
  answers the server did not mark. What Spring Security would add if the server used it; HSTS belongs
  on the proxy that owns the certificate.

Flippable: code shape `SetupCode.generate` (12 characters, 3 groups); the cap `GLOBAL_MAX_FAILURES`
(30) and `GLOBAL_WINDOW` (1 min); the allowlist default in `application.yaml`; the headers in the
client's Caddyfile. Not built, on purpose: per-address throttling (behind the proxy every address is
the proxy's unless the header is trusted; the global cap needs no trust), a CAPTCHA (bots that reach
the login are already capped; the owner is the only user), rate limits on search and download routes
(they need a login; a logged-in owner is not a bot).
