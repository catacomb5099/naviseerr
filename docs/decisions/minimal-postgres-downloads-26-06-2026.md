## Decision: Stash previous persistence work, rebuild from scratch

**Context:** The previous session's persistence work introduced a lot of concepts at once (multi-table schema, Flyway, JDBC + R2DBC dual driver, JSONB, Testcontainers, provider ref hierarchy). The developer has limited practical knowledge of these topics and could not evaluate whether the design was sound.

**Options Considered:**
1. *Keep and refine the existing work* — review and trim the previous changes incrementally.
2. *Stash and rebuild from scratch* — discard the current approach, start from the cleanest possible baseline, add one concept at a time.

**Final Choice:** Option 2 — stash and rebuild.

**Rationale:** The primary goal is learnable, reviewable increments. A single-table, single-endpoint slice is the right first step. The stash preserves the previous work for future reference without it blocking the current design.

## Decision: schema.sql + spring.sql.init instead of Flyway

**Context:** The previous approach used Flyway with versioned migration files (`V1__...sql`) and required both a JDBC driver (for Flyway's one-shot startup migration) and an R2DBC driver (for reactive runtime). This dual-driver setup was a significant source of confusion.

**Options Considered:**
1. *Flyway with versioned migrations* — industry-standard versioned schema management; easy to evolve the schema over time with tracked, reversible-in-principle migrations. Requires JDBC driver alongside R2DBC.
2. *spring.sql.init with schema.sql* — Spring Boot's built-in schema init runs a single SQL file on startup over the existing R2DBC connection. No extra driver, no migration tooling. `CREATE TABLE IF NOT EXISTS` makes it idempotent. Simpler to understand.

**Final Choice:** Option 2 — `spring.sql.init` with `schema.sql`.

**Rationale:** For a first slice with one table, Flyway's versioning overhead and dual-driver setup are not justified. `spring.sql.init` is built into Spring Boot, uses the same connection the app already has, and is immediately understandable. Flyway can be introduced later as a deliberate step when the schema starts to evolve across deployments.

**Trade-off to be aware of:** `spring.sql.init` runs the whole script on every startup. `CREATE TABLE IF NOT EXISTS` handles the idempotency. If column changes are needed later (e.g. adding a column), `schema.sql` alone cannot express that migration safely — that is the point where Flyway becomes the right tool.

## Decision: TEXT + CHECK constraint for status column (not a native Postgres ENUM)

**Context:** The `downloads.status` column needs to only allow a fixed set of values (`PENDING`, `IN_PROGRESS`, `FAILED`, `SUCCEEDED`). The question was how to enforce that constraint at the DB level.

**Options Considered:**
1. *Native Postgres ENUM type* (`CREATE TYPE download_status AS ENUM (...)`) — most semantically correct type; column literally cannot hold any other value. Downside: R2DBC's Postgres driver does not automatically map a native pg enum to a Java enum. Requires registering an `EnumCodec` on the `ConnectionFactory`, casting parameters in queries (`$1::download_status`), and `ALTER TYPE ... ADD VALUE` for future additions (which has transaction quirks).
2. *TEXT + CHECK constraint* (`CHECK (status IN ('PENDING', ...))`) — Postgres still rejects any value outside the allowed set at the DB level. R2DBC maps a Java enum to/from a `TEXT` column automatically by calling `.name()` with zero extra configuration. Adding a new status is a one-line change to the constraint.
3. *Plain TEXT, validate in Java only* — simplest, but the DB itself would not enforce valid values.

**Final Choice:** Option 2 — `TEXT` + `CHECK` constraint.

**Rationale:** Provides DB-level enforcement (ruling out Option 3) without the R2DBC codec complexity of a native enum (ruling out Option 1). The Java `DownloadStatus` enum is the source of truth in code; the `CHECK` constraint is the DB-side safety net. This is the right trade-off for a learner-friendly, reactive stack.

## Decision: R2dbcEntityTemplate.insert() instead of repository.save()

**Context:** When inserting a new `Download` entity whose `downloadId` is a UUID generated by the application (not the database), Spring Data R2DBC's `save()` method inspects the `@Id` field. If it is non-null, `save()` issues an `UPDATE`, not an `INSERT` — resulting in 0 rows affected for a new entity.

**Options Considered:**
1. *`R2dbcEntityTemplate.insert(entity)`* — always issues an `INSERT`, regardless of whether the `@Id` is set.
2. *Implement `Persistable<UUID>` on the entity* — override `isNew()` to return `true`, allowing `save()` to detect the entity as new and issue an `INSERT`.
3. *Let the database generate the ID* (e.g. `gen_random_uuid()` as column default, `@Id` left null before save) — `save()` would detect a null `@Id` and issue `INSERT`, then the DB-generated value is returned.

**Final Choice:** Option 1 — `R2dbcEntityTemplate.insert()`.

**Rationale:** Most explicit and easiest to understand. The intent (`INSERT` this row) is clear from the method name. `Persistable` adds boilerplate to the entity. DB-generated UUIDs are also valid but shift ID generation out of the app, which adds a round-trip and makes the ID less predictable in tests.
